# ADR-0017: An enum is text with a CHECK constraint, not a Postgres ENUM

- **Status:** Working
- **Confidence:** Medium
- **Decided:** 2026-07-27
- **Last reviewed:** 2026-07-27

## Context

`schema.Enum("status", "draft", "live")` declares a column constrained to a
fixed set of values. Postgres offers a native type for exactly this —
`CREATE TYPE status AS ENUM (...)` — and it is the obvious choice right up to
the point where the list has to change.

Editing a list of statuses is one of the most ordinary schema changes there is.
It should be the cheapest kind of migration, and with a native enum it is close
to the most expensive:

- **A value cannot be removed.** Postgres has no `ALTER TYPE … DROP VALUE`. The
  only route is to create a replacement type, rewrite every column using the
  old one, and drop it — a table rewrite per column, authored by hand.
- **`ALTER TYPE … ADD VALUE` could not run inside a transaction** before
  Postgres 12, and still cannot be used in the same transaction that then reads
  the new value. Migrations are applied inside a transaction here by default,
  and [ADR-0014](0014-migrations-and-import.md) already documents what
  file-scoped transaction control costs: a change that needs `NO TRANSACTION`
  drags every unrelated change in the file out of its transaction too.
- **The type is a schema-level object, not a table-level one.** Under the table
  prefixing of [ADR-0015](0015-module-isolation.md), two modules that both
  declare a `status` enum collide in a namespace neither of them owns —
  precisely the collision prefixes exist to prevent.

Set against that, the native type buys storage compactness, a defined sort
order, and type-level rejection of a bad value at every call site rather than at
insert time.

## Decision

An enum column is rendered as `text` with a named `CHECK` constraint listing the
permitted values:

```sql
"status" text NOT NULL,
CONSTRAINT "posts_status_check" CHECK ("status" IN ('draft', 'live'))
```

Changing the value list is a `DROP CONSTRAINT` followed by an `ADD CONSTRAINT`,
which the diff engine already does for every other constraint. There is no
special case, no new object type, and no transaction exception.

Removing a value is not marked destructive. It cannot lose data: Postgres
rejects the whole `ADD CONSTRAINT` if any row violates it. It carries a comment
naming the values that are no longer permitted, because the fix is in the rows
rather than in the schema, and that is not obvious from the SQL.

Codegen is unaffected either way: `Type.GoType()` already emits a Go string type
with one constant per value, and that is where a mistyped value gets caught in
practice.

## Consequences

**What this buys.** Editing a value list is an ordinary, transactional,
reversible migration generated by machinery that already existed. Nothing in
the enum path needs a lock the rest of the migration was not already taking.
Module isolation holds, because a `CHECK` constraint is named after its table
and inherits the table's prefix. The column reads as `text` to every client,
driver and introspection tool without a type lookup.

**What this costs.** More storage than a native enum's four bytes, though the
difference only matters at a scale where the column would be normalised anyway.
No implicit ordering: `ORDER BY status` sorts alphabetically rather than by
declaration order, and a schema that needs declaration order has to say so with
an explicit `CASE`. A bad value is rejected at insert time by the constraint
rather than at parse time by the type system, so the error arrives later and
names the constraint rather than the column's intent.

## What would change our mind

- If a schema needs enum values ordered by declaration rather than
  alphabetically, and the `CASE` workaround shows up in more than one or two
  places, that is a real gap — but the answer is probably an explicit ordinal
  column, not a native enum.
- If a consumer's tooling (an ORM, a GraphQL bridge, an admin UI) reads
  `pg_enum` to discover permitted values and cannot be taught to read
  `pg_constraint` instead, the discoverability argument becomes concrete rather
  than theoretical.
- If profiling ever shows the text column's width mattering on a table large
  enough to care about, revisit — but expect the answer to be a lookup table.

## Cost of change

Low to moderate, and asymmetric in the useful direction. Nothing outside
`migrate/ddl.go` knows the representation: `GoType()` already returns `string`,
the query engine treats the column as text, and the filter grammar compares it
as text. Switching to a native enum means a new DDL path, a `CREATE TYPE`
ordered before its tables, a per-module naming scheme to avoid the collision
above, and a migration converting existing columns — real work, but confined
and mechanical.

Switching *away* from a native enum later would be considerably worse, since it
would mean rewriting every table that used one. Starting from text is the
cheaper direction to be wrong in.

## Alternatives considered

**Native Postgres `ENUM`.** The strongest alternative, and it wins on storage,
sort order and type-level safety. It lost on migration cost: it makes the most
routine change to an enum — removing a value — the single most expensive kind
of migration in the system, and it puts type names in a namespace that module
prefixing does not reach.

**A lookup table with a foreign key.** Correct, fully migratable, and what a
value list should become once it acquires attributes of its own (a label, a
sort order, an active flag). Rejected as the default because it turns a
three-word declaration into a table, a seed migration and a join, for a list
that mostly never changes. This stays the recommended escalation, not the
starting point.

**Text with no constraint at all**, relying on the generated Go constants.
Rejected: the constants only bind Go callers, and the database is reachable by
migrations, admin tools and other services. A constraint that exists only in
one client is not a constraint.
